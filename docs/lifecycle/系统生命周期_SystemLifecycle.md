# ETL-Agent 系统生命周期管理

状态：首期治理基线

本文定义 ETL-Agent 从需求、设计、开发、验证、发布、运行到退役的生命周期。它和业务需求分离：需求定义“做什么”，本文定义“如何有序、可审计地交付和维护”。

## 1. 生命周期阶段

```text
需求澄清
  -> 架构与风险评审
  -> MVP 迭代开发
  -> 集成/安全/验收测试
  -> 预发布验证
  -> 受控生产发布
  -> 运行监督与持续改进
  -> 版本升级或退役
```

每个阶段必须产生可追踪的输入、输出、责任人和退出条件。未满足退出条件时，问题进入待办或风险台账，不通过口头约定进入下一阶段。

## 2. 角色与责任

| 角色 | 生命周期责任 |
| --- | --- |
| 产品负责人 | 确认业务范围、优先级、验收和未决项 |
| 架构负责人 | 维护架构、ADR、技术债和扩展边界 |
| 开发负责人 | 拆分任务、实现、代码评审和变更说明 |
| 测试负责人 | 测试策略、质量门禁、缺陷分级和验收证据 |
| 安全负责人 | 数据分级、Secret、权限、威胁建模和安全放行 |
| 运维负责人 | 环境、部署、备份、监控、发布和回滚 |
| Maker/Checker/Operator/Auditor | 运行时业务职责，不能与研发审批混同 |

小团队可以一人承担多个生命周期岗位，但同一生产变更的“实现”和“放行”必须保留独立复核记录；运行时 Maker 不得自批。

## 3. 阶段定义与门禁

### 3.1 需求澄清（M0）

输入：`主要需求_MainRequirements.md`、业务场景、数据源/目标约束。

输出：整理版需求、范围清单、角色矩阵、验收标准、未决问题和需求追踪 ID。

退出条件：首期链路、数据分级、预算、LLM Provider、部署边界和责任人已确认；未确认内容标记为 `TBD`，不得伪装成既定约束。

### 3.2 架构与风险评审（M1）

输入：需求基线和 MVP 范围。

输出：系统架构、详细设计、数据模型、API 契约、威胁模型、ADR、部署拓扑。

退出条件：控制面/数据面边界、状态隔离、Harness 三阶段协议、Secret 流程、失败/回滚路径和扩展点通过评审。

### 3.3 MVP 迭代开发（M2）

输入：已评审设计和优先级 Backlog。

输出：代码、迁移、配置、单元测试、接口文档、变更日志。

退出条件：功能有自动化测试；每个副作用入口经过 Harness；不存在未记录的临时绕过；`uv.lock`、`.env.example` 和部署文档同步。

### 3.4 集成、安全与验收测试（M3）

验证 PostgreSQL、Redis、MinIO、Vault、百炼和 SeaTunnel 的真实契约；执行权限边界、重放、防泄露、超预算、取消和回滚测试。

退出条件：P0/P1 缺陷为零；关键验收场景有日志、审计事件和测试报告；Benchmark 基线已冻结。

### 3.5 预发布验证（M4）

在与生产拓扑相近的环境执行迁移演练、备份恢复、灰度数据和容量检查。生产 Secret 不得复制到测试环境；测试数据必须脱敏。

退出条件：发布包、配置清单、数据库迁移、回滚包、监控告警、值班联系人和变更窗口均已确认。

### 3.6 生产发布（M5）

采用小批量、可回滚发布。先执行数据库兼容迁移，再发布控制面，再发布 Worker/SeaTunnel 适配器，最后开放新功能开关。

退出条件：健康检查通过、Outbox 无积压、错误率和延迟在阈值内、审计链可验证；否则按回滚预案恢复。

### 3.7 运行与持续改进（M6）

持续收集运行成功率、质量拒绝率、P0/P1 拦截率、LLM 延迟/成本、队列积压、资源使用和审计异常。Prompt、策略或模型变更必须版本化并通过 Benchmark，不能直接覆盖生产版本。

### 3.8 退役（M7）

停止新任务入口，等待或取消存量运行，完成最终审计和数据导出，撤销 Capability/Secret，归档制品和 Benchmark，最后删除或冻结数据卷。退役必须保留可审计的时间线和负责人。

## 4. 环境晋级

| 环境 | 用途 | 数据与权限 |
| --- | --- | --- |
| Local | Windows/PyCharm 快速开发 | 脱敏 Fixture；可调用百炼测试模型；不接生产库 |
| Dev VM | Ubuntu `192.168.181.128` 集成开发 | Docker Compose 基础设施；开发 Vault；隔离账号 |
| Test/Staging | 预发布和 L0/L1/L2 验证 | 脱敏或合成数据；接近生产拓扑 |
| Production | 受管数据集成 | 外置 Secret/KMS、独立权限、备份和审批 |

环境之间只提升不可变制品和版本化配置，不复制运行时数据库、Redis 数据或 Secret。

## 5. 变更、版本和回滚

- 代码、数据库迁移、Prompt、策略、连接器和 SeaTunnel 配置分别有版本号，并在制品清单中关联。
- 破坏性 API/Schema 变更采用兼容期和迁移窗口；先加字段/接口，再切换调用，最后清理旧契约。
- 生产变更必须包含影响范围、风险、监控指标、回滚步骤和验证命令。
- 回滚代码不等于回滚数据；数据面必须依靠影子表、原子 Swap 和受管清理实现业务回滚。
- 紧急变更也必须事后补齐评审、审计和测试证据。

## 6. 生命周期指标

首期至少跟踪：需求变更率、版本交付周期、P0/P1 缺陷数、自动化测试通过率、发布成功率、回滚次数、Outbox 延迟、任务成功率、质量拒绝率、LLM 成本/延迟和审计事件完整率。
